# 受控中文

受控语言解决的是同一件事：**读的人必须照着做，而且问不到作者**。航空业为这件事做了 ASD-STE100，让维修工不可能读错扭矩值。中文一直没有这样一套东西，但中文的读者同样问不到作者——跨部门的同事、外包、供应商、三个月后的自己、以及正在执行你 prompt 的 AI。

英文的歧义来自「一个词多个意思」和「一句话多种结构」。中文的歧义来自另外四处地方，照搬英文规则一条也治不到：

| 中文的歧义源 | 长什么样 | STE 为什么治不了 |
|---|---|---|
| **零指代** | 「已完成，请查收。」谁做的？谁收？ | 英语几乎不允许省略主语，STE 不需要这条规则 |
| **意合** | 「文件没备份会丢。」是条件、警告，还是事实陈述？ | 英语必须写 if / because / unless，逻辑关系天然外显 |
| **空词** | 尽快、适当、必要时、原则上、相关部门 | 英语的 hedge 是 may / might（作者的信心），中文的空词是**没想清楚** |
| **数量与范围** | 「3 日以上」「3 个工作日」含不含本数、算不算节假日 | 英文没有「以上/以下」含本数的国标惯例 |

最后一行不是修辞问题，是纠纷来源。中国有一份公开的官方规范管着它，见 `references/rules.md`。

## 什么时候用

- 一段中文通知、制度、SOP、需求、报错、工单，读完之后**不确定该做什么**。
- 文本要交给另一个部门、外部供应商、另一个 agent、或者翻译管线执行，**读错有代价**。
- 你在写 prompt、system message、工具描述，想在模型看到之前先把口子堵上。
- 你想要**前后对照**，看清违反了哪条规则、改完为什么更好。要就说——默认输出只有改写后的正文（见「输出格式」）。

不用在：创意文案、营销稿、文学、需要语气和留白的地方。受控中文是故意平淡、字面化的。

## 两档

改写前先选档。用户没说就按文本类型推断，**不要**在输出里宣布选了哪档。

**执行档** —— 制度、SOP、通知、合同与规则条款、工单、报错、工具描述、agent 指令、需求文档。凡是「读错会做错」的地方。三层规则全执行，包括硬性字数上限和词义锁定。

**阅读档** —— README、复盘、周报的叙述部分、公众号、解释性文章。第一层（指代与逻辑）和第三层（情态保护）全执行；第二层里**有纠纷代价的**（义务词、范围词、时限单位、空词）仍然执行，其余（行话、套话、一词一义）降为方向。行文需要一点弹性，全锁死读起来像换了作者，而不是变清楚了。

## 依据与范围

这份技能有两块地基，成色不一样，用之前先分清：

- **第一层「指代与逻辑」** 来自中文的语法事实：主语可以省略、分句可以只靠语序和逗号连接。这块靠描述就能执行，可以放心硬套。
- **第二层「词义锁定」** 里有一半是**有官方依据的**：《立法技术规范（试行）（一）》（全国人大常委会法工委，2009）第 13、14、15、24、25 条明确规定了「和 / 以及 / 或者」的主次、「应当 / 必须」的统一、「不得 / 禁止」的分工、「以上 / 以下 / 以内」含本数而「不满 / 超过」不含本数、「日 / 工作日」的区别。这套规范是给立法者写的，但它解决的是**中文没有形式标记**的问题，在日常制度和合同里同样成立，所以本技能直接引用。
- **第二层的另一半**（行话、套话、空词、虚动词）是本技能自己定的词表，不是国标。它可核对，但它是意见：`references/lexicon.md` 是完整清单，你可以改。改之前先想清楚，一个团队里两个人都按自己的想法改，等于没标准。

**不做什么承诺**：本技能不是法律意见，不保证条文有效。合同、法务、合规文本改完仍需法务过一遍。它修的是**形式**，不是**效力**。

## 三层规则

### 第一层 · 指代与逻辑（中文特有，执行）

| 规则 | 这样做 | 不要这样 |
|---|---|---|
| 主语落地 | 「运维在周二 22:00 执行上线。」 | 「已完成，请查收。」——谁完成、谁查收 |
| 逻辑显性 | 「如果签名不匹配，脚本就跳过该文件。」 | 「签名不匹配，跳过该文件。」——是条件还是描述？ |
| 责任句四件套 | 谁 + 做什么 + 交付什么 + 什么时候： 「运维组在 T 日 22:00 前执行上线，产出上线记录。」 | 「由运维部门负责，相关部门配合。」——配合什么、到几号 |
| 一句一动作 | 「打开文件。读第 3 行。比对签名。」 | 「打开文件并读取第 3 行，然后比对签名。」 |
| 句长 | 指令句 ≤ 25 字，说明句 ≤ 40 字（汉字计，标点不计） | 一句话套两层从句再挂一个补充说明 |
| 不用分号串动作 | 拆成两句，或改成列表 | 「先开票；再发货。」 |
| 「的」链 ≤ 2 层 | 「高并发场景下，把配置项改对。」 | 「提高系统在高并发场景下的稳定性相关的配置项的修改」 |
| 列表化 | ≥ 3 步或 ≥ 3 个条件，用编号列表 | 把四步塞进一个自然段 |
| 中英混排 | 中文用全角标点，代码和标识符用反引号包住 | 「注意: 调用sync()即可,不要重试」 |

### 第二层 · 词义锁定（可核对）

左侧标「国标」的，依据是《立法技术规范（试行）（一）》，可以在法务场合直接引用；标「词表」的，依据是本技能自己的清单。

| 规则 | 依据 | 这样做 | 不要这样 |
|---|---|---|---|
| 义务词锁定 | 国标 14 | 全篇统一用「应当」（或统一用「必须」，二选一） | 应当 / 必须 / 务必 / 须 混着用 |
| 禁止词锁定 | 国标 15 | 有主语用「不得」（任何单位不得…），无主语祈使用「禁止」（禁止吸烟） | 严禁 / 不准 / 不应 / 不宜 轮着来 |
| 并列词锁定 | 国标 13 | 「和」= 无主次；「以及」= 前者为主；「或者」= 选择 | 「和/或」、顿号与「以及」混用导致分不清是并列还是要全选 |
| 范围边界 | 国标 24 | 以上 / 以下 / 以内**含本数**；不满 / 超过**不含本数**；怕读者算错就写成 `≥ 3 个工作日` | 「3 天以上」——读者不知道含不含第 3 天 |
| 时限单位 | 国标 25 | 「日」含节假日，「工作日」不含。写清起算点和终点 | 同一份文件里「3 日」和「3 个工作日」并用 |
| 空时间词 | 词表 | 写出时长或截止时间；实在定不了写 `【待定：截止时间】` 并在末尾「未定」行列出 | 尽快、及时、第一时间、后续、稍后 |
| 空条件词 | 词表 | 写出触发条件；不设条件就明说「本条不设条件」 | 必要时、视情况、酌情、原则上、按需 |
| 空数量词 | 词表 | 写数字、单位、阈值 | 适当、适量、若干、一定程度、加大力度 |
| 空主体 | 词表 | 写岗位或角色：「内容运营组」 | 相关部门、有关人员、相关材料 |
| 去虚动词 | 词表 | 分析日志。 | 对日志进行分析。/ 予以处理。/ 作出安排。 |
| 去行话 | 词表 | 说具体做了什么 | 赋能、抓手、闭环、打通、链路、颗粒度、对齐、沉淀 |
| 去套话 | 词表 | 直接说事 | 需要注意的是、众所周知、在一定程度上、不难看出 |
| 不用双重否定 | 词表 | 「有风险」 | 不无道理 / 未必不可 / 不能不 |
| 一词一义 | 词表 | 定一个名字，全篇用它（全程「用户」） | 用户 / 客户 / 使用者 / 会员 混用；删除 / 移除 / 清除 混用 |
| 术语首次定义 | 词表 | 首次出现给一句定义，之后只用它 | 抛一个自造词，后面全靠猜 |

### 第三层 · 情态保护（优先级最高）

**情态是内容，空词不是。** 这条区分是全文最容易踩坏的地方，判别口径只有一句：**把词删掉，句子的真假会不会变？**

- 会变 → **情态**。可能、也许、大概、估计、大概率、或许、不排除、我判断——这些是作者给出的置信度，删掉就是换结论。句长上限最爱引诱人删掉的正是它们。**保留**，哪怕句子因此变长。字数上限与情态冲突时，情态赢。
- 不会变 → **空词**。尽快、适当、必要时、原则上、酌情、相关部门——这些**不是**信心，是没写清楚。必须换成时间、条件、数字，或者留成待定项。

两个硬约束，跟这条一起用：

1. **不许造数字。** 「尽快」不能改成「24 小时内」——原文没说，那是你补的事实。只能改成 `【待定：修复时限】`，并写进「未定」行。
2. **不许补原因、频率、机制。** 改写后读起来更顺，是因为它补了一个原文没有的解释，那已经不是改写了。丢掉不确定性的改写比原文更危险，因为它看起来更可信。

## 扫描清单

六种习惯覆盖了中文工作文本被误读的绝大多数情形。每一种都是机械的：你能指出具体那个字、那个词或那个标点，不需要审美判断。改写之前先扫一遍。

1. **无主句** —— 「已完成」「待确认」「未通过」。读者不知道谁做、找谁。改法：补主语。
2. **逗号链** —— 一句话里三个逗号、没有任何「如果 / 因为 / 除非」，逻辑关系全靠读者补。改法：把逻辑词写出来，或者拆句。
3. **空词** —— 尽快、适当、必要时、原则上、相关部门。改法：换成数字、条件、主体；定不了的留占位符，不要编。
4. **虚动词** —— 进行 / 加以 / 予以 / 作出 / 给予 + 名词。改法：用后面的动词。
5. **行话与套话** —— 赋能、抓手、闭环，需要注意的是、众所周知。改法：说具体做了什么，或者删掉。
6. **「的」链** —— 三个「的」串成一串定语，读者要倒着拆。改法：拆两句，或把定语改成动作。

## 流程

1. 选档（执行档 / 阅读档）。不要宣布。
2. 通读一遍，先弄清它改完之后**还必须说什么**。没读懂不要动笔。
3. 逐句走。对照三层规则和扫描清单标出每一处。机械首查可以跑 `scripts/zh-lint.py`（stdin 或文件参数，`--json` 出结构化结果）：它查分号串联、半角标点、空时间 / 空条件 / 空数量 / 空主体、虚动词、行话、套话、双重否定、义务词轮换、范围词未标含不含本数、时限单位混用、超长句、逗号链、无主状态句、「被」字句无施事、「的」链、同义轮换、列表项没说完。`--baseline N` 容忍存量文档的 N 处硬违规；`--disable 规则名` 关掉指定规则。它**不查零指代和意合**（要句法分析），也**永不查情态**。
4. 逐句重写。原则只有一个：**原意一个字不能变**。
   - 动笔前先看情态。原文是「可能」就写「可能」，不能升成事实。
   - 空词要么填数字，要么留待定项。落法看缺的东西在读的时候起不起作用：
     - 句子缺了它读不通（「在【待定：截止时间】前提交」）→ 句内写 `【待定：X】`。
     - 句子本身读得通、只是少了一条约束（「系统生成报表，并在页面显示状态」）→ 正文不动，末尾用「未定」行列出。
   - 改短会丢掉必要的精度（安全条件、例外、范围、数字）时，保留长的写法，加「保留原样」行，不要悄悄简化。
5. 按「输出格式」输出。档位选择与规则分析留在内部。
6. 原文本来就合规，就直说合规，别硬改。

## 输出格式

**默认：只给改写后的正文。** 调用方要的是能直接粘进通知、条款、工具描述、prompt 的结果。把改写后的文本单独打印：不要加技能介绍、档位声明、违规计数、变更摘要、规则表，也不要结尾再问一句「需要我解释吗」。

两行允许的附加，在正文之后，没有就不写：

```
未定：提交截止时间（原文「尽快」，需产品负责人补充）
保留原样：保留了「不排除第三方接口抖动的可能」，因为改写会把它升成事实
```

- `未定：` —— 每个占位符一行，写明缺的是什么、该谁补。
- `保留原样：` —— 故意没简化或没改短的地方，写明会丢什么精度。

**用户要求看理由时（「给我看 diff」「违反了哪些规则」「解释一下改了什么」「前后对照」），输出规则表：**

```markdown
| 违反的规则 | 原文 | 改写后 |
|---|---|---|
| 空时间词 | 「上线前尽快提交申请」 | 「上线前【待定：提交时限】提交申请」 |
| 无主句 | 「已完成，请查收。」 | 「内容运营组已导出 6 月报表，请你查收。」 |
| 范围未标边界 | 「3 天以上提交」 | 「≥ 3 日提交」 |

档位：执行档。共 3 处。
```

表后加一行说明**故意没有改**的地方和原因（通常是：再简化会丢精度，或需要原文之外的信息）。

## 边界

**会做：**
- 把含糊、空词多、边界不清的中文改写成单义、有主语、有数字的句子。
- 默认只给改写后的正文；用户要求时列出用到的规则。
- 保留原文的每一个事实、条件、范围和数字。
- 保留每一处情态的强度，不添加原文没有的断言。
- 把定不下来的空词变成 `【待定：…】` 占位符，而不是编一个数字。
- 给必须保留的自造术语提一行定义。

**不会做：**
- 声称改写后的文本有法律效力。合同、条款、合规文本改完仍需法务过一遍。
- 改写创意、营销、说服性文案 —— 那里的语气和留白才是重点。
- 把「尽快」改成「24 小时内」，把「可能已失败」改成「失败」，把「可能是 X 导致的」改成「X 是原因」 —— 前者是编事实，后两者是换结论。
- 为了短而悄悄删掉安全条件、例外、起算点 —— 会标注这个取舍。
- 保证「合规」。这是受控写作思路的通用清晰化工具，不是认证工具。
- 把空内容变有用。受控中文修的是**形式**，不是**内容**。一段空话改完会变成一段干净、简短、标点正确的空话。文本本身没东西可说，就直说，不要粉饰。
- 为了短牺牲可读性。删字不是目的，消歧才是。压到某个程度之后，省下的时间会被读者重新花回去 —— 句子没有歧义就停手，不要追求最短。

- **`examples/before-after.md`** —— 前后对照：通知、制度条款、需求、报错、agent 指令、设计说明，含「保留原样」和「未定」的实际用法，以及一个「本来就合规、不要改」的例子。
